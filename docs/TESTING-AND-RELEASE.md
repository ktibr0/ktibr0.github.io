# Проверки и выпуск

## Порядок

Основной агент формирует критерии и исполняемые тесты, Luna 6 medium реализует ограниченный этап, отдельная Luna 6 low запускает тесты (запрос 16.10.2026). Основной агент читает результаты и код, просматривает изображения. Исполнитель тестов не исправляет ожидания. Для чистой документации достаточно ссылок, diff/границ и Git-проверок; игровые тесты не повторять без изменения кода/риска.

Тестировать живую HTML/CSS/JS-страницу через HTTP(S), реальные нажатия как верных, так и неверных действий; прямой вызов API не доказывает наличие обработчика на кнопке. Не выдавать геометрические PASS за визуальную приёмку. Уже обнаруживались схлопнутые span-карточки и зеркальные скрытые буквы в WebKit, несмотря на зелёную часть tests.

Размеры: Chromium + WebKit, 1024×768, 1180×820 landscape; 412×915 и 360×800 portrait; 1024×600 для небольшой доступной высоты. Проверять safe area, zoom, reduced motion, длинный текст, поворот, восстановление партии, достижимость всех controls. Предпочтительно зоны нажатия 44px+, на тесной телефонной клавиатуре проверять практическую читаемость/высоту. При ограничениях физического iPad/Samsung явно писать «не проверено на устройстве».

## Готовые проверки Криптографа

Из Git root:

```text
node tests/cryptographer/rules.cjs
node tests/cryptographer/acceptance.cjs
```

Первый script требует Node и исходный commit `9fbe121` в истории. Второй требует Playwright/его browsers. Настройка и optional env vars описаны в `tests/cryptographer/README.md`. Нет необходимости добавлять Playwright/Node в поставку для игроков.

В этой Windows-сессии были доступны (перепроверять, не считать универсальными):

- Node: `C:/Program Files/nodejs/node.exe`.
- Playwright: `C:/Users/alex_/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules/playwright`.
- Chromium: `C:/Users/alex_/AppData/Local/ms-playwright/chromium_headless_shell-1243/chrome-headless-shell-win64/chrome-headless-shell.exe`.
- WebKit: `C:/Users/alex_/AppData/Local/ms-playwright/webkit-2359/Playwright.exe`.

В runner можно передать `PLAYWRIGHT_CHROMIUM_EXECUTABLE`, `PLAYWRIGHT_WEBKIT_EXECUTABLE`; `PLAYWRIGHT_MODULE_ROOT` для acceptance указывает каталог `.../node/node_modules`, не сам пакет playwright. Имена browser revisions не должны становиться зависимостью проекта. При sandbox ACL/localhost/spawn проблемах использовать системный pwsh и узкое разрешение, а не менять tests.

## Новые проверки

- Sumplete: чистые правила, solver с подсчётом до двух, неоднозначные fixtures, корректность clues/диагонали, ограничение генерации, no mutation, save migration и повреждённое/недоступное storage. E2E: клик/цикл состояния/undo, hint, ошибки, reload, новая партия и разные размеры. Изменение начальных зелёных клеток должно быть осознанным решением контракта.
- ArcoMage: см. подробные сетевые/кеш/SW критерии в `ARCOMAGE-SELF-HOSTING.md`; важна заблокированная внешняя площадка в чистом контексте, а не прогретый внешний кеш.
- RSVP: настоящий игровой старт и действия, а не metadata/isPlaying. Тестовый black screen/headless AudioContext — наблюдение среды, пока не воспроизведено на целевом устройстве.

## Git-проверки

Перед каждым commit/push прочитать `git status --short --branch`, `git remote -v`, последние commits, tracked/untracked и staged diff. Проверить секреты/ключи/credential-файлы. Stage только выбранные пути; не `git add .` вместе с пользовательским ZIP. `git diff --cached --check` должен пройти; при ошибке остановиться. На Windows проверять exit codes каждой зависимой команды.

Для одного этапа сохранять осмысленные commits, не переписывать опубликованную историю. `forgejo` — резерв/рабочая история; `origin` — GitHub Pages. Перед push проверить remote ref и отсутствие новых чужих commits. Если remote ушёл вперёд — исследовать/интегрировать, не force-push. Инструкции SSH и shell в AGENTS.

## Публикация игрового этапа

1. Сохранить локальные журналы и изображения в `_work/<этап>/`, краткий результат и ограничения в docs, обновить TODO/HANDOFF.
2. Проверки прошли и основной агент принял diff/визуал → commit → push Forgejo и GitHub. Отправлять только рабочую ветку; не менять remotes.
3. Сверить `git ls-remote forgejo refs/heads/main` и `git ls-remote origin refs/heads/main` с локальным HEAD (ветку перепроверить). Статус рабочего дерева может содержать нетронутый пользовательский ZIP — это нормально.
4. Проверить Pages workflow для конкретного HEAD: статус `completed`, conclusion `success`. Успешный push ещё не означает успешную публикацию.
5. Проверить публичные HTTP 200 и соответствие ожидаемым файлам (учитывая CRLF/LF), выполнить smoke опубликованной игры в обоих движках: данные, действие, reload/сохранение, отсутствие page errors.
6. Не сообщать «опубликовано», пока публичный адрес не отдаёт принятую версию. При задержке сообщать этап, не повторять частые неизменившиеся проверки; при ошибке сохранять результат и разбираться в причине.
